Full writeup in docs/findings/13-rank-aware-metrics.md.

  With the threshold knob gone (drg-exact collapses all five rows) and the K
  knob gone (MRR has no K), this is the first number the project has produced
  with ZERO reported knobs. 76 winnable cases, mean-of-per-fold-rates:

                      MRR@50   Hit@1   Hit@50    P@1     P@50   coverage
    Bio_ClinicalBERT  0.2462  0.1749   0.6967  0.1749  0.0290    1.0000
    BiomedBERT        0.2432  0.1693   0.6656  0.1693  0.0280    1.0000
    BlueBERT          0.2314  0.1549   0.7300  0.1549  0.0316    1.0000
    BioSentVec        0.2029  0.1484   0.3577  0.1484  0.0857    0.8477

  NO PAIR SEPARATES. Max |t| over all six pairs: 1.718 (winnable), 1.651
  (all-cases), 1.174 (answered) -- all under the 2.262 needed for p<0.05. The
  written-in-advance prediction held on every population.

  PRECISION@K INVERTS THE TOP-K CURVE, as designed. It FALLS with K for every
  arm (6.0x from K=1 to 50 for Bio_ClinicalBERT) where TOP-K rises for every
  arm, and it is NOT monotone (BioSentVec 0.0868 -> 0.0845 -> 0.0855 ->
  0.0858 -> 0.0857), so unlike Hit@K nothing forces its direction. Within-arm
  only: truncating your own candidate list inflates reported P@K 3.53x.

  THE UNPREDICTED RESULT - A THIRD KNOB WAS UNDERNEATH. MRR is not abstention-
  neutral: a declined case scores RR=0 while an arm that always offers 50
  candidates has some chance of a hit. The baseline abstains; the BERT arms
  never do. So the CONVENTION reorders all four arms:

    abstention scores 0     Bio_ClinicalBERT > BiomedBERT > BlueBERT > BioSentVec
    abstention excluded     BioSentVec > Bio_ClinicalBERT > BiomedBERT > BlueBERT
                            (0.1474)     (0.1321)          (0.1302)     (0.1229)

  EVERY SIGN FLIPS; the baseline goes last to first. Neither convention is
  neutral and THERE IS NO THIRD THAT IS -- penalising abstention charges "I
  don't know" the same as a wrong answer, while excluding it scores the
  baseline on 98 self-chosen cases against the BERT arms' 129. Abstention is a
  property of the ARM, not of the metric, so this knob cannot be designed away.
  All three populations are reported; the conclusion survives all three.
  Quantifying the self-selection half of it is P40.

  THE VALIDATION THAT MAKES IT TRUSTWORTHY. RankMetrics.txt's three populations
  reproduce legacy's P / R / PR columns EXACTLY, from an independent code path:
    R  0.19230769230769232 == all-cases Hit@10
    P  0.25124098124098121 == answered  Hit@10
    PR 0.75576923076923075 == coverage
  Exact to the last bit, and predicted in rank_metrics.py's N2 note before the
  code existed. This also RETIRES the degeneracy confusion for good: P == R was
  never the metric collapsing, it is PR == 1.0, i.e. the answered and all-cases
  populations being the SAME SET because those arms never abstain. The columns
  were never wrong, only unlabelled.

===============================================================================
THE 58.1% CEILING - READ BEFORE DESIGNING ANY EXACT-MATCH METRIC
===============================================================================
The method predicts by copying an answer from a retrieved patient, so the answer must
EXIST in the pool to be copied. 145 unique diagnosis descriptions across 129
admissions; 105 of them (72.4%) occur exactly once in the whole dataset.
Only 75 of 129 test cases (58.1%) have their correct DRG present anywhere in their
fold's training pool. The other 41.9% are unwinnable under exact matching - not
because retrieval is bad, but because the answer is not in the library.
A PERFECT RETRIEVER THEREFORE CAPS AT 58.1% UNDER EXACT MATCH.

Three ways to handle it, in order of preference:
  1. Graded relevance - partial credit for a same-family DRG. Raises the ceiling and
     is more clinically sensible than all-or-nothing.
  2. Report against the ceiling - "X of a possible 58.1%". Honest and standard.
  3. Restrict evaluation to the 75 winnable cases and say so. Cleanest signal,
     smallest n.

NOTE: measured on the CURRENT, LEAKY folds. Re-measure after P2. Neither plan says so.

[ ] P39. THE TWO ARMS BREAK SCORE TIES DIFFERENTLY
        Effort: ~an hour of code + one 43-min golden run. Found 2026-08-06 while
        implementing P5. NOT urgent -- measured impact is below the effect size --
        but it is a cross-arm divergence with no defensible reason to exist.

        The two arms rank candidates with different sorts:
          BERT     bert_models.py:177  similarities.sort(key=..., reverse=True)
                   Python's sort is STABLE -> ties break by training-set order
          baseline cython_utils.py:278  np.argsort(-1 * similarity_array)
                   defaults to quicksort, which is NOT stable -> ties break
                   arbitrarily, and not reproducibly across numpy versions

        Hit@K barely notices, because it only asks whether ANY of the top K
        cleared the bar. MRR reads the rank directly, so a tie at the front
        changes the score.

        MEASURED, all 129 real test cases, StubEncoder at 768D, drg-exact labels:
          tied pairs (any score tie)                    83
          test cases with any tie                       81 / 129
          tied pairs where relevance DIFFERS             1   <- the only ones
          cases where MRR depends on tie order           1 / 129
          ties at the rank-1 MAX pick                    1 (order-sensitive: 0)

        Ties are COMMON but almost never consequential: two candidates tie when
        they share the winning symptom for every test symptom, which is
        structural and encoder-independent, but they then usually carry the same
        relevance, so no order can change a metric.

        IMPACT BOUND. The rank-1 tie is not order-sensitive, so the one affected
        tie sits at rank >= 2, giving an RR delta <= 1/2 - 1/3 = 0.1667 and an
        MRR shift <= 0.0022 on the 76-case winnable population. Inter-arm deltas
        measured on the same runs are 0.0015-0.0067, so this is at the bottom of
        that range rather than above it. A rank-1 order-sensitive tie WOULD have
        mattered (0.0066, squarely inside the range) -- worth re-measuring if the
        data or the encoder ever changes.

        CAVEAT ON THE MEASUREMENT: it used StubEncoder, so the specific ties are
        not the ties a real encoder produces. What transfers is the mechanism and
        the order of magnitude, not the count of 1.

        FIX: np.argsort(..., kind="stable") so both arms break ties identically.
        That MOVES NUMBERS, so it goes behind the config seam as a `ranking`
        field defaulting to legacy, exactly like preprocess_version and grader --
        and it needs its own golden run. Do NOT fold it into an existing pipeline
        name silently; a reader must be able to tell which ranking produced a
        table.

        Worth doing because "the arms are comparable" should be true by
        construction, not by an impact bound that happens to be small this time.

P40  PER-CASE OUTPUT - the only thing blocking the test P5 could not run
     Priority: HIGHEST of the open non-blocker items. Found 2026-08-06 while
     writing up P5.

     WHY IT IS SUDDENLY VALUABLE. It has been on the known-defects list for
     months as a cosmetic wart. P5 turned it into the binding constraint on the
     one question P5 raised and could not answer.

     THE QUESTION. P5 found that how you treat abstention reorders all four
     arms. The `answered` population (abstentions excluded) puts BioSentVec
     FIRST; `winnable`/`all-cases` (abstentions score 0) put it LAST. Every
     sign inverts. So the obvious doubt about `answered` is SELF-SELECTION: the
     baseline chose which 98 of 129 cases to answer, so those 98 may simply be
     the easy ones, and comparing its MRR on 98 self-chosen cases against the
     BERT arms' 129 is not a matched comparison.

     THE TEST THAT ANSWERS IT. Compute each BERT arm's MRR restricted to the
     baseline's 98 answered cases, and compare against its MRR on all 129. If
     the restricted figure is higher, those cases ARE easier and `answered`
     flatters the baseline by a measurable amount. That is a matched
     comparison, and it is the only way to put a number on the confound.

     THE TRAP - DO NOT USE THE RATIO. MRR_all-cases / coverage looks like it
     bounds the effect and returns ~1.0, which reads as "confound is 0.5%, move
     on". It is ALGEBRAICALLY IDENTICAL to MRR_answered: abstentions contribute
     0 to the all-cases numerator, and coverage is exactly the denominator
     ratio, so the quotient is MRR_answered by construction and carries zero
     information. This was computed, believed for about a minute, and withdrawn
     on 2026-08-06. The warning is now in analyze_rank_metrics.py's docstring
     and in finding 13, because it is convincing enough to fool a careful
     reader twice.

     WHY IT IS BLOCKED. The test needs the per-case relevance vector for each
     (arm, HADM_ID). RankMetrics.txt carries only per-fold and 10-FOLD
     aggregates. The per-case files that would carry it are ALL EMPTY:
       cython_utils.py:203-204 opens the two handles
       cython_utils.py:308-309 closes them
       ... with NOTHING written in between
       bert_models.py:539-540  never opens them at all, yet still mkdir's Fold*/
     (line numbers re-resolved 2026-08-11; they had drifted ~140 lines)
     The baseline emits 258 zero-byte files. Neither arm has EVER produced
     per-case output.

     SCOPE, and the reason it is not a golden risk: write a NEW sibling file
     (RankCases.txt or per-case rows inside RankMetrics.txt) rather than
     repairing the two dead handles. PerformanceIndex.txt stays untouched, so
     the byte-exact golden still covers exactly what it covered before -- the
     same reasoning that made P5 additive. Repairing the dead handles is a
     separate, lower-value cleanup.

     DATA-USE CONSTRAINT: per-case output is keyed by HADM_ID, so it is
     DUA-covered and must stay under results*/ (gitignored by glob) and out of
     docs/. Only aggregates go in findings. The pre-commit hook's 20-distinct-
     HADM_ID rule is the second line of defence, not the first.

     REPORTABLE EITHER WAY. If the 98 are no easier, `answered` stops being
     suspect and the baseline's first place there becomes the honest headline.
     If they are easier, that quantity IS the confound and belongs in the
     README. There is no outcome in which this measurement is wasted.
